## 1. 当前产品基础

SearchDBPad 已是具备多引擎基础的数据管理客户端，下一阶段应围绕日常工作流程深化体验。

| 范围 | 当前基线 | 本次讨论应关注的增量 |
|---|---|---|
| 引擎与查询 | 内置 Elasticsearch、OpenSearch、Solr adapter；ES/OpenSearch 使用 DSL，Solr 使用原生参数 | 共用工作区体验，同时保留各引擎的语义和能力差异 |
| 查询编辑 | DSL 已有多标签、重命名、格式化、执行和按标签保存结果；标签仅在当前内存中保留，切换连接或资源会重置 | 跨切换和重启保留草稿、执行历史、编辑辅助与结果配置 |
| 收藏与连接组织 | DSL 收藏和连接分组已有本地持久化 | 明确收藏、草稿、历史、模板之间的关系，避免重复建设 |
| 导入导出 | 已有按能力选择格式、有限批次、流式文件处理、进度与取消；导出最多 10,000 条 | 更大规模导出、失败恢复和长期任务管理 |
| 任务可见性 | 已有当前会话的导入导出任务列表与取消状态 | 任务历史和恢复语义仍需单独设计 |
| 连接与认证 | 当前提供无认证和 Basic Auth | 扩展企业环境所需认证、证书、凭据存储与防误操作 |

## 2. 同类产品观察

公开资料核查时间：**2026-10-18**。以下比较基于官方文档与项目公开介绍，未对每个产品逐项安装实测，也不是完整的功能优劣排名。表中的启发属于产品机会假设，仍需通过目标用户的真实任务验证。

| 产品 | 官方资料展示的重点 | 对 SearchDBPad 的启发 |
|---|---|---|
| [Elasticvue](https://github.com/cars10/elasticvue#features) | 桌面、浏览器扩展和 Web 形态；文档、索引、分片与 REST 管理 | 基础管理功能的完整性很重要，下一步可从操作效率形成价值 |
| [Dejavu](https://github.com/appbaseio/dejavu#2-features) | 可视化筛选、文档编辑、导入导出和搜索预览 | 数据处理流程是否顺畅，直接影响使用频率 |
| [Kibana Console](https://www.elastic.co/docs/explore-analyze/query-filter/tools/console) | 补全、变量、历史和请求导入导出 | 编辑、执行、查找、复用查询应构成连续流程 |
| [OpenSearch Relevance Workbench](https://docs.opensearch.org/latest/search-plugins/search-relevance/using-search-relevance-workbench/) | 3.1 引入的工作台提供搜索结果比较、相关性评估和实验 | 可借鉴搜索质量验证流程；其插件 API 不等于本项目 OpenSearch 1.x/2.x 基线已有能力 |
| [DBeaver Enterprise](https://dbeaver.com/docs/dbeaver/Enterprise-Edition/) | 多数据库桌面管理，包括 Elasticsearch 支持 | 借鉴成熟的连接组织、工作区与结果操作习惯 |

机会假设：在已有多引擎基础上，先让用户持续积累和复用查询工作，再围绕排障或搜索质量选择特色，可能比同时扩大所有功能面更容易形成清晰体验。这不是对竞品缺失能力的断言。

## 3. 五个候选方向

### A. 查询工作台升级

**用户价值：** 昨天的查询今天能继续，常用查询容易找回，多标签切换不丢上下文；减少重复编辑和复制粘贴。

**建议首版边界：**

- 持久化查询历史，记录目标连接、资源、查询内容、执行时间和结果摘要。
- 恢复查询标签与草稿，明确切换连接、切换资源、关闭标签和重启的行为。
- 增加清楚的执行/停止状态和正文保存控制，保持请求隔离与取消语义。
- 整理已有收藏的入口及复用动作，补充语言信息，明确历史与草稿的关系。

**扩展项：** A2 的基础字段补全、结果列选择与类型提示，以及 A3 的参数化模板和跨连接复用。收藏分组、查询文件导入导出、多请求脚本是更后续候选。详细草案建议简单查询与 Solr 原生参数也纳入首期历史/表单恢复；是否扩展为多标签仍待讨论，不能默认只有 DSL 用户需要恢复工作。

**相对成本：** A1 中等；A2、A3 分批评估。先做历史与草稿可缩小范围，完整多引擎补全和参数模板会明显增加工作量。

**依赖与风险：** 标签和连接的归属关系、存储上限与清理、敏感查询内容的本地保留、删除连接后的恢复、过期请求与取消。结果本体是否持久化必须明确，不能随草稿自动无限保存。

**优先级假设：** 首选方向。详见[详细草案](2026-10-18-query-workbench-discussion.md)，其中所有默认值仍待讨论。

### B. 跨环境对比

**用户价值：** 排查“测试环境正常，生产环境异常”时，快速发现配置、字段和数据差异。

**建议首版边界：**

- 用户显式选择两侧连接和资源，先从同引擎或同协议族对比开始。
- 只读对比 Mapping/Schema、Settings、别名以及文档数量。
- 对比指定 ID 的文档；展示字段路径、两侧值和差异类型。
- 支持过滤差异和导出报告，保留采集时间与目标信息。

**扩展项：** 保存对比配置、忽略动态字段、定期采集快照、选择性生成变更建议；自动同步需另行定义权限、确认和恢复方案。

**相对成本：** 中；只读配置对比较容易形成完整流程，全量文档对账则属于更大的范围。

**依赖与风险：** 版本默认值差异、动态元数据、权限不足、采样与数量统计误差、两侧采集时间不一致。跨引擎 Schema 语义不能简单按 JSON 等值比较。

**优先级假设：** A 之后的特色候选，适合开发、测试和发布排障用户。

### C. 搜索调试工具

**用户价值：** 围绕“为什么搜不到、为什么排在这里、为什么查询慢”缩短排查路径。

**建议首版边界：**

- 分词/分析结果展示，明确目标字段、分析器和实际输入。
- 同一资源上两条查询的结果并排比较，展示 ID、排名和关键字段差异。
- 固定样本文本与查询条件，便于修改后重复验证。

**扩展项：** Explain 展示、Profile 可视化、测试查询集、相关性指标和实验记录。可参考官方 [Kibana Search Profiler](https://www.elastic.co/docs/explore-analyze/query-filter/tools/search-profiler) 的分析流程。

**相对成本：** 中高；解释评分、性能与相关性评估各自都有独立复杂度，不宜一次全部纳入首版。

**依赖与风险：** 引擎专有 API、版本和权限差异、昂贵调试请求、结果波动，以及不同查询的评分不可直接等量比较。必须按能力展示入口。

**优先级假设：** 与 B 二选一作为阶段性特色更容易聚焦；搜索研发用户占主导时优先考虑 C。

### D. 可靠的大批量数据处理

**用户价值：** 数据量增加、部分数据错误或任务中断时，用户能够知道发生了什么，并可靠地继续处理。

**建议首版边界：**

- 在现有流式处理、批次、进度和取消之上，按引擎能力支持超过 10,000 条的分页导出。
- 明确导出进度、结果完整性、取消后的文件处理与资源清理。
- 导入失败行下载，提供错误分类和显式重试入口。
- 明确任务日志的保留范围，先区分“查看历史”和“中断后恢复”。

**扩展项：** 可恢复任务、字段映射、跨连接复制、跨引擎迁移、冲突策略与数据校验。

**相对成本：** 高；扩大数量上限只是表面变化，真正成本在分页一致性、失败处理和恢复语义。

**依赖与风险：** ES/OpenSearch 的分页/PIT/游标能力、Solr 的 cursor 语义、索引变化、磁盘空间、权限与长任务资源释放。导入重试需要定义 ID、幂等和重复写入行为。

**优先级假设：** 经常搬运大量数据的用户有明确需求时前置；否则分阶段推进，避免挤占日常查询体验。

### E. 生产环境连接与防误操作

**用户价值：** 连接实际公司环境更顺畅，并在高风险操作之前清晰识别当前目标。

**建议首版边界：**

- 按引擎支持扩展认证与自定义 CA，明确支持矩阵和连接测试结果。
- 增加环境标识、生产连接醒目提示，以及客户端只读模式。
- 将认证信息迁移到系统凭据存储，并处理旧配置兼容和迁移失败。
- 为已有破坏性操作补齐目标名称、影响范围和明确确认。

**扩展项：** HTTP 代理、SSH 隧道、更多凭据提供方、操作审计。认证、网络连通和防误操作可分成更小批次。

**相对成本：** 中高；单项视觉标识成本较低，凭据迁移和连接链路需更完整的安全及环境验证。

**依赖与风险：** 引擎认证差异、Windows 凭据库、便携版使用环境、证书校验、迁移回退。客户端只读用于防误操作，服务端账号权限仍应决定实际访问能力。

**优先级假设：** 连接受阻或生产误操作风险已影响使用时前置；不能仅因其列在 E 就视为低优先级。

## 4. 建议顺序与组合

| 假设的主要用户/任务 | 建议组合 | 建议顺序 |
|---|---|---|
| 开发、测试与日常排障 | A + B | 先保留与复用查询，再连接两侧工作上下文做对比 |
| 搜索研发与查询调优 | A + C | 先建立稳定的查询工作区，再沉淀分析与比较流程 |
| 数据导入导出频繁 | A + D | 先解决最影响使用的数据可靠性缺口，工作台按小批次并行规划 |
| 内网、云服务和生产集群 | E + A | 先打通实际连接条件，再完善查询体验 |

当前建议是 **A 优先，随后选择 B 或 C**；D、E 根据真实使用阻碍前置。相对成本不是工期估算，也没有绑定 `0.4.1`、`0.5.0` 或其他版本号。

每个方向都需要持续穿插兼容性和稳定性验收。多引擎实际支持范围、失败状态、取消、过期响应、敏感信息处理与破坏性确认，应随选定功能完成，不单独拖到“最后统一补”。

## 5. 下一轮需要确认的问题

1. 主要使用者是谁：开发、测试、搜索研发、数据处理，还是运维？最高频的三个任务是什么？
2. A 中最急迫的损失是什么：找不回查询、切换丢草稿、重启丢标签、字段难写，还是结果难看？
3. ES/OpenSearch 与 Solr 在实际使用中的占比如何？首版是否要求三种查询入口同时完善？
4. 当前是否存在连接受阻、生产误操作风险或超过一万条的数据处理需求，足以让 D/E 前置？
5. A 完成后，更希望产品在“跨环境排障”还是“搜索调试”上形成特色？
6. 对查询正文的本地持久化、默认历史保留量和清理方式有何要求？是否存在必须排除的敏感查询？
